# 手机UFS跑分很快，为什么重载时还会卡死重启？

<div class="article-meta"><span class="badge">📘 模块六 · 高速接口一致性测试 · 第 10 篇 · 手机存储接口 · UFS</span><span class="badge">⏱ 约 63 分钟</span><span class="badge qr">🔧 含工程师速查</span></div>


一台UFS 4.x手机工程样机，冷机启动正常，短时间顺序读写也很快。连续进行高清视频录像、应用安装和大文件读写后，吞吐开始下降，99.9%延迟明显拉长，系统偶发卡顿。

最严重的一次，Kernel Log先后出现UIC相关错误、Power Mode Change失败和UFS Host Reset，手机随后重启。重新启动后UFS器件仍能识别，但某次日志显示链路只恢复到更低Gear或单Lane。

看到这里，很容易出现六种结论：

- SLC Cache写满了；
- UFS芯片坏了；
- PCB信号质量不够；
- 电源掉压；
- UFS驱动有Bug；
- 高温导致存储降速。

这些都可能成为调查方向，却都不能只凭现象直接成立。

现在还缺四组关键证据：

1. 性能下降时，Gear、Lane、Power Mode和Hibern8状态有没有先变化？
2. 第一个错误来自UFS Command、UTP、UniPro、M-PHY、电源、REF_CLK还是RST_n？
3. Host到Device和Device到Host，究竟是哪一个方向、哪一条Lane先异常？
4. 吞吐下降是否能在没有任何链路错误的情况下，仅随温度、WriteBooster或Flash后台维护复现？

这篇文章就从这四组证据开始。跑分只说明某段时间内完成了I/O，不证明所有Gear、Lane、方向和低功耗切换都有足够Margin。

![图1：同一台UFS 4.x手机短时间顺序读写正常，持续录像、安装应用和大文件读写后出现Latency拉长、UIC错误、Host Reset与重启；图中同时保留Flash、Protocol、M-PHY、Power和Thermal问号，证明重载只是触发条件而不是根因结论](/images/44/ill01_case.png)

## 第1章　UFS是什么、应用在哪里

### 1.1 UFS是Managed Flash Storage，不只是一颗NAND

UFS全称Universal Flash Storage，由JEDEC定义。它把NAND Flash、内部Controller、缓存、错误管理和标准化高速接口封装成一个Managed Storage Device，广泛用于手机、平板、车载系统、边缘计算和部分PC。〔S1〕〔S2〕

从系统角度看，UFS器件同时包含两类对象：

- **存储对象**：NAND Array、映射、缓存、垃圾回收、磨损管理和内部Firmware；
- **高速接口对象**：UFS Command、UTP、UniPro、M-PHY、参考时钟、电源和复位。

因此，“UFS性能下降”可能发生在闪存内部，也可能发生在链路或系统层。只看一个顺序读写数字，无法判断是哪一类。

### 1.2 UFS与eMMC不是同一条总线

eMMC使用并行数据、Command和Clock结构；UFS则使用MIPI M-PHY高速差分Lane和UniPro链路，具备独立发送与接收方向、命令排队和更完整的低功耗状态管理。

本篇只讨论UFS，原因不是eMMC不重要，而是两者的物理层、测试点、仪器和报告模型差异太大。把它们塞进同一篇，只会让“存储接口”变成一张版本表，而不是可执行的测试教程。

### 1.3 能开机不等于链路健康

手机能进入系统，至少说明：

- 电源、复位和参考时钟完成了基本启动；
- Host能够发现UFS Device；
- Link Startup和设备初始化至少成功过一次；
- Boot LUN或系统分区能够被读取；
- 当前条件下没有立即触发不可恢复错误。

它不能自动证明：

- 所有支持Gear都能稳定工作；
- 两个方向、两条Lane都具备足够Margin；
- Hibern8反复进入退出可靠；
- 高温、低电压和长时间压力下没有错误；
- Tx、Rx和Channel满足正式一致性要求；
- NAND持续写入性能满足产品目标。

### 1.4 跑分也不能替一致性测试签字

顺序读取、顺序写入、随机IOPS和Latency都是重要产品指标，但它们回答的是“当前软件负载下，系统完成I/O的表现”。

一致性测试还要回答：

- Host和Device分别发得对不对；
- 两端Receiver在最坏合规输入下能不能收；
- Package与PCB Channel是否满足预算；
- Link Startup、Power Mode和Hibern8是否正确；
- 电源、REF_CLK和RST_n是否稳定；
- 错误恢复有没有掩盖反复发生的底层问题。

**性能测试、协议测试和电气测试是三套证据，不能互相冒充。**

## 第2章　传输原理和代际差异

### 2.1 UFS从上到下有三大层

UFS通信可以先按三层理解。〔S9〕

**Application Layer**负责：

- UFS Command Set；
- Task Manager；
- Device Manager；
- 设备配置、Query和电源管理请求。

**UFS Transport Protocol，简称UTP**负责：

- Command、Task和Device Management消息；
- 把这些消息封装成UPIU；
- 在Host与Device之间运输请求和响应。

**UFS Interconnect Layer，简称UIC**由两部分组成：

- UniPro：Transport、Network、Data Link、PHY Adapter等链路功能；
- M-PHY：实际的高速电气收发器。

![图2：从Android或系统I/O、SCSI/UFS Command、UTP与UPIU、UniPro、M-PHY一直到SoC Package、PCB和UFS Package逐层展开；右侧把Performance、Protocol、PHY与Power证据分开，证明Command Timeout、UIC Error和眼图Fail不是同一个层次](/images/44/ill02_stack.png)

一笔读取可以简化成：

```text
Application / File System
  → UFS Command
  → UTP Request UPIU
  → UniPro
  → M-PHY Host Tx
  → PCB Channel
  → M-PHY Device Rx
  → UFS Device内部取数
  → Device Tx返回Data / Response
```

链路里任何一层异常，都可能最终表现成“应用卡顿”，但后续证据完全不同。

### 2.2 UFS是独立收发方向，不是共享双向差分对

M-PHY使用差分信号和Embedded Clock，不需要像传统MIPI D-PHY显示链路那样单独放一条Forwarded Clock Lane。〔S5〕〔S8〕

常见UFS物理连接可以写成：

```text
Host Tx Lane 0/1  → Device Rx Lane 0/1
Host Rx Lane 0/1  ← Device Tx Lane 0/1
```

每条Lane是单向的。Host的发送线接Device的接收线，Device的发送线接Host的接收线。独立的Tx与Rx Lane组合成全双工链路。

这会直接影响测试点选择：

- Host→Device方向，要关心Device实际收到什么；
- Device→Host方向，要关心Host实际收到什么；
- 两个方向不能只量一组线后统一写成“UFS波形正常”。

![动图1：Host通过独立Forward Lane发送Command或Write Data，Device通过Reverse Lane返回Read Data与Response；两条方向可同时活动，随后链路进入Hibern8并恢复。动画明确UFS使用Embedded Clock和独立Tx/Rx Lane，不存在单独Forwarded Clock Lane，也不是一对差分线轮流双向驱动](/images/44/anim01_full_duplex.gif)

### 2.3 Gear、Lane、Rate和Power Mode不要混成一个数字

一份UFS日志至少要把下面几项分开：

| 项目 | 回答什么 |
|---|---|
| Gear | 当前使用哪个速率等级 |
| Active Tx Lane | 当前发送方向启用了几条Lane |
| Active Rx Lane | 当前接收方向启用了几条Lane |
| Rate / Series | 当前Gear下适用的具体速率系列 |
| Power Mode | FAST、SLOW或适用自动模式等链路工作方式 |
| Link State | Active、Hibern8、Off或恢复过程 |

只写“UFS 4.0”不能证明当前真的运行在HS-G5 x2。

同样，“链路恢复成单Lane”只是一条状态证据。它可能来自：

- 能力协商；
- 错误恢复；
- 固件策略；
- 某一方向或Lane的Margin；
- 电源与温度；
- 测试模式配置。

没有前后时间轴，不能把单Lane直接写成PCB坏了。

### 2.4 Link Startup与Hibern8

UFS上电或重置后，需要完成Host Controller初始化、Link Startup、Device初始化和Power Mode配置。链路空闲时，又可能进入Hibern8降低功耗。

需要重点关注的不是背一张固定状态图，而是记录：

1. Link Startup是否一次成功；
2. 最终协商到什么Gear和Lane；
3. Power Mode Change是否成功；
4. Hibern8进入和退出是否稳定；
5. 失败后执行了哪一级恢复；
6. 恢复后Gear、Lane和性能是否发生变化。

旧代际和不同实现可能走低速启动路径；M-PHY v5.0和UniPro v2.0已经引入High-Speed Startup能力，UniPro v3.0进一步要求High-Speed Link Startup。〔S5〕〔S6〕〔S7〕

所以不能把“上电一定先PWM-G1，再固定切到HS-G5”画成所有UFS版本唯一流程。

### 2.5 UFS 3.x、4.x和5.0怎样理解

| UFS代际 | 主要互连层 | 公开最高Lane速率 | 公开能力边界 |
|---|---|---:|---|
| UFS 2.x | HS-G3等级 | 约5.8Gb/s/lane | 旧代际背景 |
| UFS 3.0/3.1 | M-PHY v4.1 HS-G4 + UniPro v1.8 | 约11.6～11.7Gb/s/lane | 两Lane约23Gb/s/方向 |
| UFS 4.0/4.1 | M-PHY v5.0 HS-G5 + UniPro v2.0 | 23.32Gb/s/lane | JEDEC公开有效读写最高约4.2GB/s |
| UFS 5.0 | M-PHY v6.0 HS-G6 + UniPro v3.0 | 46.694Gb/s/lane | 两Lane有效顺序读写最高约10.8GB/s |

UFS 4.1于2024年12月发布，保持与UFS 4.0的硬件兼容，主要增强Device Management、WriteBooster、Exception和安全等能力，并没有把PHY提升到G6。〔S3〕〔S4〕

UFS 5.0已于2026年2月正式发布，采用M-PHY v6.0和UniPro v3.0。〔S1〕〔S2〕

### 2.6 UFS 5.0为什么不能只改一个速度数字

M-PHY HS-G6公开变化包括：

- PAM4；
- 46.694Gb/s/lane；
- 1b1b编码；
- Link Equalization与Training；
- UniPro v3.0中的RS-FEC、64-bit CRC、Lane Alignment、Precoding等。〔S5〕〔S7〕

这意味着UFS 5.0不是把G5 NRZ眼图横轴缩小一半：

- PAM4要观察三个眼；
- Tx/Rx测试方法和参考接收器会变化；
- Equalization和Training进入链路建立；
- FEC前后的错误含义不同；
- Channel和Probe要求需要重新评估。

![图3：UFS 3.x HS-G4、UFS 4.x HS-G5与UFS 5.0 HS-G6代际对照。G4/G5使用二进制高速信号示意，G6明确画成PAM4三眼，并把1b1b、FEC和Link Equalization放在独立新框架中；图中禁止把4.1写成G6，也不把UFS 5.0写成已全面量产](/images/44/ill03_generation.png)

### 2.7 46.64Gb/s为什么不等于5.83GB/s手机跑分

按M-PHY v5.0公开最高值：

```text
HS-G5 单Lane ≈ 23.32Gb/s
两Lane单方向 ≈ 46.64Gb/s
原始bit到byte换算 ≈ 5.83GB/s
```

5.83GB/s只是原始信号速率的单位换算，还没有扣除：

- PHY编码和UniPro开销；
- UTP与UPIU开销；
- Command、Queue Depth和Transfer Size；
- Host Controller与DMA；
- NAND Array和内部Controller；
- SLC Cache或WriteBooster；
- Garbage Collection与Wear Leveling；
- 温度、电源和系统调度。

JEDEC公开UFS 4.1有效读写能力为最高约4.2GB/s。产品实际结果还会受容量、NAND代际、工作负载和温度影响。〔S4〕〔S10〕

同理，UFS 5.0两Lane原始PHY带宽约93.4Gb/s，JEDEC公开有效顺序读写最高约10.8GB/s，而不是简单除以8后承诺11.7GB/s。〔S2〕

## 第3章　正确使用与设计注意事项

### 3.1 真实物理路径比框图更复杂

手机主板上的路径通常是：

```text
SoC UFS Controller / M-PHY
  → SoC Package与BGA Fanout
  → 主板Via与PCB走线
  → UFS BGA Fanout与Package
  → UFS Device M-PHY
```

虽然距离通常比外部USB、HDMI或DisplayPort短，但速率高、BGA密度大，而且几乎没有方便的连接器参考面。

需要同时关注：

- P/N差分阻抗与回流；
- Lane内Skew；
- Lane-to-Lane Skew；
- Via Stub和参考平面切换；
- Host Tx与Device Tx之间的串扰；
- 电源噪声对PHY和Clock的耦合；
- Package、Interposer与Probe的额外损耗。

“走线很短”不是不做SI分析的理由。

### 3.2 两个方向必须分别选测试点

系统Debug优先回答“对应Receiver实际收到了什么”：

| 方向 | 发送端 | 接收端 | 系统Debug首选位置 |
|---|---|---|---|
| Host→Device | SoC Host Tx | UFS Device Rx | 靠近UFS BGA Rx端的Interposer或可达Mid-bus点 |
| Device→Host | UFS Device Tx | SoC Host Rx | 靠近SoC Rx端的Interposer、专用测试结构或可达Mid-bus点 |

![图4：SoC与UFS BGA之间画出Host Tx到Device Rx、Device Tx到Host Rx两组独立差分Lane。每个方向的系统Debug发光点位于对应接收端附近；正式Tx参考面则位于CTS定义的Tx Fixture。图中同时标出Package、PCB、Interposer和未覆盖段，防止把一个Mid-bus点写成整条UFS链路](/images/44/ill04_duplex.png)

这里有三个边界：

1. **接收端附近测量是系统Debug。**它能观察Package和PCB之后的实际输入，却不等同正式Rx Conformance。
2. **正式Tx Conformance看Tx参考面。**M-PHY公开测试资料说明Tx测量以Tx Pin或CTS规定参考面为目标，Mid-bus测量需要通过S参数做Embedding或De-embedding。〔S11〕
3. **一个点不能覆盖两个方向。**Host Tx和Device Tx分别位于链路两端，必须单独测试。

### 3.3 BGA项目的测试能力要在设计阶段准备

UFS器件焊在BGA下方后，临时飞线很难提供可信结果。高速G5/G6条件下，长飞线、大测试Pad和Stub还会直接改变链路。

工程阶段建议准备：

- UFS Device BGA Interposer或Breakout；
- Host Tx和Device Tx专用Test Board；
- Inline Protocol Analyzer Interposer；
- 经过仿真的Mid-bus焊点或SMA测试版本；
- 独立Channel Coupon；
- 可访问的UFS供电、REF_CLK和RST_n；
- 良品主板与良品UFS Device；
- 可在不改变其他变量时替换的测试样机。

如果只能在链路中点测量，报告必须写清：

- 测点距离哪一端多远；
- 测点到Tx Pin和Rx Pin还有哪些结构；
- Probe和Interposer带来了什么负载；
- 是否做了Embedding/De-embedding；
- 结论能覆盖到哪个参考面。

### 3.4 电源、REF_CLK和RST_n不能当配角

UFS问题常被归到“存储”或“SI”，但真实Bring-up还依赖：

- Device所需电源轨；
- I/O或PHY相关电源；
- 电源Ramp、Droop、Ripple和瞬态电流；
- REF_CLK频率、幅度、Jitter和启停；
- RST_n电平和时序；
- Runtime PM与System Suspend；
- Host、PMIC和UFS Firmware协作。

不同UFS代际和器件的电源轨数量、命名、范围和顺序可能不同。UFS 5.0还公开增加了独立PHY供电轨，用于改善PHY与Memory Subsystem的噪声隔离。〔S2〕

所以文章、测试计划和示意图不能给所有UFS器件写一套统一电压与上电顺序。最终应回到：

- 当前JESD220版本；
- 目标UFS Device Datasheet；
- SoC Hardware Design Guide；
- PMIC和系统电源时序要求。

### 3.5 设计时就冻结可复现条件

后续报告至少要记录：

- SoC与UFS Device型号；
- UFS、UniPro和M-PHY版本；
- Host与Device Firmware；
- Kernel、Driver与Bootloader版本；
- 当前Gear、Lane、Rate和Power Mode；
- UFS容量、剩余空间和健康状态；
- WriteBooster或Cache状态；
- 温度与电源；
- 压力工具、Block Size、Queue Depth和持续时间。

否则两次“同样的跑分”可能根本不是同一个测试。

## 第4章　一致性测试到底测什么

UFS最容易出现的误区，是把整个验证缩成AndroBench、fio或一张M-PHY眼图。

完整测试至少分七个域：

| 测试域 | 主要对象 | 回答什么 | 不能替代 |
|---|---|---|---|
| Performance | Host、Device、NAND与软件 | 吞吐、IOPS、Latency和稳定性 | PHY Compliance |
| M-PHY Tx | Host Tx、Device Tx | 发出的电气信号是否合规 | Rx和Protocol |
| M-PHY Rx | Host Rx、Device Rx | 受扰输入下能否保持规定错误性能 | Tx和Channel |
| Passive Channel | Package、PCB、Via、Interposer | 无源损耗、反射、串扰和Skew | Active PHY |
| UniPro/UFS Protocol | Link、UPIU、Command、Power Mode | 协议与错误恢复是否正确 | 电气Margin |
| Power/Clock/Reset | 供电、REF_CLK、RST_n | 启动、运行和低功耗切换是否稳定 | Flash性能 |
| Interop/Stress | Host、Device、温度和电源组合 | 真实组合是否长期可靠 | 单项正式CTS |

![图5：UFS七类测试覆盖矩阵。横向按Host、PCB/Package、UFS Device与System展开，纵向为Performance、Tx、Rx、Passive Channel、Protocol、Power/Clock/Reset与Interop；实心符号表示正式测试域，三角形表示Characterization，菱形表示系统Debug证据，证明跑分和眼图都不能覆盖整张矩阵](/images/44/ill05_matrix.png)

### 4.1 Performance测试

至少区分：

- Sequential Read/Write；
- Random Read/Write；
- IOPS；
- Average、P99、P99.9和Max Latency；
- Burst与Sustained；
- 冷机与热机；
- 空盘与高占用；
- Foreground与Background Workload。

单看Average Throughput很容易漏掉卡顿。用户体验更常被长尾Latency、Command Timeout和Reset影响。

### 4.2 Tx测试

Host Tx和Device Tx都要覆盖：

- 支持的Gear与Rate；
- Lane 0和Lane 1；
- HS、PWM、SYS与适用Reference Clock项目；
- 适用Amplitude、Termination和Slew状态；
- Eye、Jitter、Common Mode、Differential Amplitude、Rise/Fall、Skew等CTS项目；
- UFS 5.0 G6的PAM4与Equalization相关要求。

Tx报告只能说明被测发送端在指定条件和参考面下的结果。

### 4.3 Rx测试

Receiver Test不是“在接收端放示波器看眼图”。

它要回答：

> 在规范允许的最坏输入下，Host Rx或Device Rx还能不能保持规定错误性能？

因此必须生成并校准Stressed Signal，再把它送进DUT Receiver，最后通过Loopback、Exerciser或错误计数读取结果。

### 4.4 Channel测试

Channel只包含无源结构：

- Package；
- BGA Breakout；
- PCB Trace；
- Via；
- Reference Plane；
- Interposer；
- Fixture。

上电工作的SoC和UFS Device不是VNA的透明无源网络。不能把VNA P1接SoC附近、P2接UFS附近，然后让测量穿过两个Active PHY。

### 4.5 Protocol与系统测试

协议分析仪和Host Log可以观察：

- Link Startup；
- Power Mode Change；
- Hibern8；
- UPIU与Command；
- Task Management和Query；
- Error Recovery；
- Host Reset与Device Reset；
- UIC相关错误；
- 哪个事件最先发生。

公开协议分析工具支持双向UniPro/UFS Capture、Trigger、Filter、Trace Validation、Corner Case和错误注入。〔S13〕〔S14〕

## 第5章　Tx、Rx、Channel分别怎么测

### 5.1 Host Tx和Device Tx要拆成两份

Host Tx方向：

```text
SoC Host Tx → Test Fixture / Probe → Oscilloscope
```

Device Tx方向：

```text
UFS Device Tx → Test Fixture / Probe → Oscilloscope
```

推荐流程：

1. 锁定UFS、M-PHY和CTS版本；
2. 确认DUT进入正确Tx Test Mode；
3. 选择方向、Gear、Rate、Lane和Pattern；
4. 选择规定Termination、Amplitude或适用状态；
5. 标记Tx Pin、Fixture或Mid-bus参考面；
6. 完成Scope、Probe、Cable和Deskew校准；
7. 应用正确的Embedding/De-embedding；
8. 运行适用HS、PWM、SYS和Reference Clock项目；
9. 保存原始波形、自动报告和Margin；
10. 找出最差方向、Lane、Gear和条件。

Tektronix公开资料列出的M-PHY v5.0 Tx项目包括Unit Interval、Frequency Offset、Common Mode、Differential Amplitude、Eye、Rise/Fall、Lane Skew和Jitter等，同时支持Mid-bus Filter。〔S11〕

### 5.2 为什么G5更偏向SMA或低噪声探测

M-PHY信号摆幅较低，G5频率高，Probe噪声、输入回损和测试支路损耗都会直接吃掉Margin。

公开仪器资料指出，G5条件下SMA类探测在噪声和输入特性方面通常更有优势。〔S11〕

这不代表“所有手机都必须焊SMA”，而是说明：

- 正式测试板要优先提供可重复的低噪声连接；
- 量产主板Mid-bus Probe更适合Debug；
- 两种接法不能不加说明地放进同一份Compliance报告。

### 5.3 Receiver Test要先校准，再接DUT

Host Rx台面：

```text
BERT / Pattern Generator
  → Stress / Embedding Channel
  → Host Rx规定参考面
```

Device Rx台面：

```text
BERT / Pattern Generator
  → Stress / Embedding Channel
  → Device Rx规定参考面
```

每个方向都分成两个阶段。

**阶段A：校准**

```text
Source → Stress Channel → Fixture → Calibration Scope
```

校准适用的：

- Amplitude；
- Jitter；
- Noise；
- Eye Opening；
- Channel；
- Equalization或Training条件；
- Pattern和Gear。

**阶段B：正式接收**

```text
Source → 相同Stress设置 → Fixture → DUT Rx
                                      ↓
                           Loopback / Exerciser / Counter
```

校准完成后，要按规定撤掉Calibration Scope或切换连接。不能长期保留额外T分支负载，再把结果写成正式Rx。

公开M-PHY测试资料同样把Receiver测试拆成受扰信号生成、校准、DUT刺激和错误判断几个环节。〔S12〕

### 5.4 Rx结果必须有可审计错误出口

可用方式可能包括：

- M-PHY Receiver Test Mode；
- Loopback；
- UFS/UniPro Exerciser；
- Vendor认可的BER Counter；
- 规定测试流程中的错误统计。

若真实UFS Device无法提供可审计的错误计数，只能写：

- 系统功能压力结果；
- Protocol Error结果；
- Characterization结果。

不能把“连续读写没有卡死”换算成正式BER Pass。

### 5.5 Channel用完整复数S参数说话

推荐四端口VNA/TDR流程：

1. 定义Host侧与Device侧参考面；
2. 确认P/N端口映射；
3. 完成SOLT、TRL或项目适用校准；
4. 测量Coupon、Interposer和Fixture；
5. 转换Mixed-Mode S参数；
6. 保存Insertion Loss、Return Loss、Crosstalk、Mode Conversion和Phase；
7. 验证去嵌后的因果性、无源性和时域结果；
8. 将Channel模型用于Tx Embedding、Rx Stress或仿真。

Channel结论要写清：

- 覆盖了Package还是只覆盖PCB；
- 是否包含Interposer；
- 是否包含Probe Pad；
- 参考面在哪里；
- UFS 4.x还是UFS 5.0目标；
- 哪个方向、Lane和频段最差。

## 第8章　判据和标准从哪里来

### 8.1 规范层级

UFS项目的判据不是来自一张网上速率表，而是来自多层文件：

1. JEDEC JESD220，对应UFS Device与Interface版本；
2. JEDEC JESD223，对应UFS Host Controller Interface；
3. MIPI M-PHY Base Specification；
4. MIPI M-PHY Conformance Test Suite；
5. MIPI UniPro Specification与CTS；
6. UFS Device Datasheet；
7. SoC Hardware Design Guide；
8. 仪器、Fixture和自动软件批准版本；
9. 产品内部Performance、Power和Thermal目标。

### 8.2 公开文章可以写什么

可以公开写：

- 规范组织和版本；
- UFS 3.x/4.x/5.0关系；
- 公开最高速率；
- UFS分层；
- Tx/Rx/Channel/Protocol方法；
- Reference Plane和校准原则；
- 公开测试工具能力；
- 报告和Debug流程。

不能从旧应用笔记、仪器截图或网络文章拼出：

- 当前M-PHY正式电压；
- Eye Mask；
- Jitter限值；
- Rx Stress参数；
- Hibern8时序；
- BER门槛；
- G6 PAM4和FEC判据。

这些值必须由项目有权使用的当前规范读取。

### 8.3 产品跑分门槛来自哪里

Performance判据还要绑定：

- 目标UFS Device型号和容量；
- 产品使用场景；
- 软件版本；
- 温度与电源；
- 测试工具；
- 数据量、Block Size和Queue Depth；
- Burst还是Sustained；
- 产品内部性能目标。

厂商写“最高4200MB/s”，不等于任何容量、温度和负载都必须达到4200MB/s。

### 8.4 Characterization与Compliance要分开

报告首页应标记：

- **Compliance**：按正式规范和批准Setup执行；
- **Characterization**：超出正式条件寻找Margin；
- **System Debug**：在真实手机上定位问题；
- **Performance Validation**：产品负载和用户体验；
- **Interop/Stress**：不同组合与环境长期可靠性。

Characterization失败不一定等于Compliance Fail；系统功能稳定也不能反向证明Compliance Pass。

## 第9章　报告怎么看

### 9.1 先确认报告有效

依次核对：

1. Host和UFS Device是不是目标型号；
2. UFS、UniPro和M-PHY版本是否匹配；
3. 测的是Host Tx、Device Tx、Host Rx还是Device Rx；
4. Gear、Rate和Lane是否正确；
5. Test Mode和Pattern是否正确；
6. Fixture、Probe和Reference Plane是否明确；
7. Embedding/De-embedding文件是否正确；
8. CTS、软件和仪器Firmware版本是否记录；
9. 电源、REF_CLK、温度和DUT Firmware是否冻结；
10. 报告属于Compliance、Characterization还是System Debug。

Setup无效时，Pass和Fail都没有结论价值。

### 9.2 找最差方向、Lane和状态

不要只看总PASS/FAIL，要找：

- Host Tx还是Device Tx；
- Host Rx还是Device Rx；
- Lane 0还是Lane 1；
- 哪个Gear、Rate和Amplitude；
- 哪个Power Mode；
- Hibern8进入还是退出；
- 哪个温度和电压；
- 哪个UPIU或Command之后首次错误；
- 哪个负载和持续时间触发。

### 9.3 把五张图对到同一时间轴

最有价值的报告不是五份PDF，而是把下面五类证据对齐：

1. Throughput与Latency；
2. Gear、Lane、Power Mode与Link State；
3. UIC、Command和Reset事件；
4. 电源、REF_CLK、RST_n和温度；
5. Protocol Trace。

![图6：UFS报告统一时间轴。顶部为Throughput与P99.9 Latency，中部依次显示Gear/Lane、Hibern8、UIC/Command/Reset事件，底部为电源、REF_CLK、温度和Protocol Trace。首个异常被单独标出，避免只看最后Host Reset后倒推根因](/images/44/ill06_report.png)

### 9.4 四种常见时间顺序

**情况A：吞吐先降，链路状态不变，也没有UIC错误**

优先调查：

- SLC Cache/WriteBooster；
- NAND内部管理；
- 温度；
- 剩余空间；
- 文件系统和后台负载。

**情况B：Power Mode Change或Hibern8先失败，之后吞吐下降**

优先调查：

- Link State；
- Host/Device Firmware；
- REF_CLK；
- 电源；
- M-PHY启动与接收Margin；
- UniPro错误恢复。

**情况C：电源或Clock先异常，随后出现UIC错误和Reset**

后续UIC错误可能只是结果。应先修复Power/Clock，再复测PHY与Protocol。

**情况D：某方向某Lane错误先增加，随后降Gear或单Lane恢复**

优先进入该方向的Tx、Rx与Channel分段，不能只看恢复后的低Gear跑分。

### 9.5 推荐结论写法

推荐：

- “在UFS 4.1、HS-G5、2-Lane、85°C和指定压力条件下，Device→Host方向Lane 1的错误计数先增加，随后发生Power Mode恢复与Host Reset。”
- “固定Gear并关闭Hibern8后问题不再复现，证据支持低功耗切换相关，但尚不能单独区分Firmware、Clock与Rx Margin。”
- “链路Gear/Lane和UIC错误均未变化，吞吐下降只随Device温度与持续写入量出现，当前证据优先指向存储内部性能行为。”
- “接收端Mid-bus波形改善且协议错误同步下降，但该结果属于System Debug，不等同正式Tx Compliance。”

不推荐：

- “UFS眼图通过，存储没问题。”
- “UIC Error说明PCB损耗超标。”
- “跑分低于4200MB/s，所以UFS 4.0不合格。”
- “降到G4后稳定，根因就是G5眼图。”

## 第10章　常见问题如何Debug

### 10.1 第一步：冻结复现条件

记录：

- 主板、SoC与UFS Device；
- Bootloader、Kernel、Driver和Firmware；
- UFS容量、剩余空间和健康状态；
- Gear、Lane、Power Mode；
- WriteBooster/Cache；
- 测试工具、Block Size、Queue Depth和数据量；
- 温度、电源和充电状态；
- 复现步骤、持续时间和首次异常时间；
- 每轮日志、Trace和录像文件名。

没有这一层，第二轮“正常”可能只是Device冷下来了或Cache恢复了。

### 10.2 第二步：先确认当前链路到底跑在哪

读取并保存：

- Tx Gear与Rx Gear；
- Active Tx Lane与Active Rx Lane；
- Rate；
- Power Mode；
- Link State；
- Hibern8计数；
- Power Mode Change结果；
- Error Recovery和Reset记录。

“产品支持UFS 4.0”与“当前工作在HS-G5 x2”不是同一句话。

### 10.3 第三步：先分Performance下降还是Link异常

把问题分成两类。

**只有Performance下降**

- Gear/Lane不变；
- 无新增UIC或Command错误；
- 无Power Mode失败；
- 无Reset；
- 吞吐随写入量、温度或剩余空间变化。

优先查Flash、Cache、GC、Thermal和软件负载。

**Link同时异常**

- Gear/Lane发生变化；
- UIC错误增加；
- Hibern8或Power Mode失败；
- Command Timeout；
- Abort、Device Reset或Host Reset。

继续进入Protocol、Power、Clock和PHY调查。

### 10.4 第四步：把第一个错误钉在时间轴

常见顺序：

```text
性能负载开始
  → 电流增加
  → 某电源出现Droop
  → UIC错误
  → Command Timeout
  → Host Reset
  → 吞吐归零
```

也可能是：

```text
持续写入
  → Device温度上升
  → 吞吐下降
  → Gear/Lane不变
  → 无任何UIC错误
```

这两条链路的根因方向完全不同。

### 10.5 第五步：做低侵入可控A/B

| A/B动作 | 主要隔离对象 |
|---|---|
| 冷机 ↔ 热机 | Thermal、PHY Margin和Flash后台行为 |
| 原电压 ↔ 允许范围内Margin电压 | Power Integrity与Receiver Margin |
| Hibern8开 ↔ 关闭 | 低功耗进入退出 |
| 自动Power Mode ↔ 固定目标模式 | 协商、策略与链路稳定性 |
| HS-G5 ↔ HS-G4 | 速率相关PHY/Channel问题 |
| 2-Lane ↔ 1-Lane | Lane相关问题与Lane间影响 |
| Read ↔ Write ↔ Mixed | Host/Device方向、Flash负载与电流 |
| 原UFS Device ↔ 良品Device | Device与主板相关性 |
| 原主板 ↔ 良品主板 | SoC、PCB与供电相关性 |

每次只改一个变量，并恢复原条件回换验证。

### 10.6 第六步：分别看两个方向

若Write更容易触发，不能直接说Host→Device方向有问题，因为写入还会改变：

- UFS Device内部NAND活动；
- Device电流；
- 温度；
- Response和Flow Control；
- Host与Device的双向协议流量。

需要用Trace和错误方向确认：

- Host→Device Lane是否先出现问题；
- Device→Host Lane是否先出现NAC/CRC或其他错误；
- 哪个方向的Tx/Rx/Channel与错误同步变化；
- 只改单一方向的测试条件后现象是否跟随。

### 10.7 第七步：Power、Clock和Reset同步检查

重点观察：

- UFS相关电源Droop与Ripple；
- 高I/O负载下的电流瞬态；
- REF_CLK是否中断、漂移或Jitter变差；
- RST_n是否出现毛刺或非预期Assert；
- Runtime PM和System Suspend时电源是否按预期保持；
- UFS 5.0 PHY独立供电是否受到Memory Subsystem噪声影响。

如果Power或Clock先异常，先修这一层。不要带着已知供电问题继续解释后续眼图和协议错误。

### 10.8 第八步：进入接收端测点和协议Interposer

当低侵入证据指向链路后：

1. Host→Device方向先看靠近Device Rx的可达点；
2. Device→Host方向先看靠近Host Rx的可达点；
3. 使用相同Probe、带宽和Filter比较良品与问题板；
4. 记录Interposer/Probe负载；
5. 同时抓Protocol Trace；
6. 只在需要区分Tx与Channel时回查发送端；
7. 正式结论再进入CTS Test Board。

![动图2：UFS持续压力Debug统一时间轴。动画先显示吞吐和Latency，再离散高亮Gear/Lane、Hibern8、UIC Error、电源与REF_CLK，最后才出现Host Reset；随后测量环分别切换到Device Rx端和Host Rx端，证明应先找首个异常和错误方向，而不是让箭头沿链路滑动后直接宣布某个器件损坏](/images/44/anim02_debug_timeline.gif)

### 10.9 第九步：进入Tx、Rx和Channel正式分段

若问题只在高Gear出现：

- 分别运行Host Tx与Device Tx；
- 分别运行Host Rx与Device Rx；
- 测对应Channel和Interposer；
- 比较Lane 0/1；
- 比较冷机/热机和电压角；
- 记录Equalization、Amplitude和Slew设置；
- Fail点复测并更换Fixture确认。

系统波形“看起来变差”只能帮助缩小范围。关闭问题前，要回到正式参考面和测试流程。

### 10.10 按现象收口

| 现象 | 第一层证据 | 下一步 | 避免误判 |
|---|---|---|---|
| 开机偶发不识别 | Power、RST_n、REF_CLK、Link Startup | 协议Trace、低Gear、良品A/B | 直接换UFS芯片 |
| 只能较低Gear | Gear/Lane与Power Mode记录 | 对应方向Tx/Rx/Channel | 把低Gear当根因 |
| 只启用单Lane | Active Lane与错误方向 | Lane 0/1 A/B、Breakout与Rx | 只看总吞吐 |
| Hibern8退出失败 | 首错时间、Clock和Power | 关闭Hibern8、固定模式、Firmware | 冷机正常就判无问题 |
| UIC Error增加 | PA/DL等错误分类 | Direction、Protocol、Power、PHY | UIC Error等于PCB坏 |
| Command Timeout/Reset | 首个UPIU与前置错误 | Device响应、Link、Power和Firmware | 只看最后Reset |
| 短跑分快、持续写慢 | Gear/Lane、错误、温度 | Cache/GC/Thermal与链路并行排查 | 直接判M-PHY |
| 仅高温或低压失败 | 温度、电压和方向 | Rx Margin、Power、Clock与Channel | 只降频绕过 |

### 10.11 修复后恢复原失败条件

可能修复包括：

- 调整Flash Firmware、WriteBooster或后台管理策略；
- 修正Host Driver、Power Mode和Error Recovery；
- 改善UFS电源、去耦、REF_CLK或RST_n；
- 修改Tx Slew、Amplitude或Equalization；
- 改善BGA Breakout、Via、参考平面或串扰；
- 改善Receiver设置或Training；
- 修正Interposer和测试支路；
- 更新SoC或UFS Device Firmware。

关闭问题前，必须恢复：

- 原主板和Device组合；
- 原UFS Gear、Lane和Power Mode；
- 原视频录像、应用安装或I/O脚本；
- 原数据量和持续时间；
- 原温度和电源；
- 原Hibern8/Runtime PM条件；
- 原高占用或低剩余空间状态。

最终报告应能连成：

> 改变了什么 → 哪个物理或协议指标改善 → 首个错误怎样变化 → 原卡顿/重启是否消失 → 其他方向、Gear、Lane和低功耗状态有没有退化。

这才是一条完整的UFS Debug闭环。

## 写在最后

UFS最容易误判的地方，是“性能”和“链路”最终都会表现成手机卡顿。短跑分很高，只能说明当前缓存、温度、软件和链路状态组合下完成了一段I/O；UIC Error、Gear下降和Host Reset，又只能证明链路或恢复过程出现了异常，并不会自动告诉我们根因在PCB、UFS Device还是供电。

正确方法是先把UFS分成Command/UTP、UniPro、M-PHY、Channel和Power，再把Host→Device与Device→Host两个方向分开。最后把Throughput、Latency、Gear、Lane、Hibern8、错误、电源、温度和Protocol Trace放在同一条时间轴上。

### 11.9 跑分掉速与链路异常决策树

2. 记录Gear、Lane、Power Mode和Link State；
3. 对齐Throughput、Latency、UIC、Command和Reset；
4. 若链路状态不变且无错误，先查Cache、GC、Thermal和软件；
5. 若Power Mode/Hibern8先失败，查Firmware、Clock、Power和Rx；
6. 若电源或Clock先异常，先修首因；
7. 若某方向某Lane先报错，进入对应Tx/Rx/Channel；

9. 必要时进入正式Tx/Rx Test Mode；
10. 修复后恢复原重载、温度和低功耗条件。

### 11.10 正文不可写死

- UFS 4.1是截至2026年的最新版本；
- UFS 5.0已经在所有量产手机普及；
- 两个方向带宽相加就是存储性能；
- 46.64Gb/s除以8等于手机必须达到5.83GB/s；
- 跑分Pass等于UFS一致性Pass；
- 持续写入掉速一定是M-PHY问题；
- UIC Error一定是PCB或UFS芯片损坏；
- 低Gear或单Lane就是根因；
- UFS使用共享双向差分对；
- UFS有独立Forwarded Clock Lane；
- 所有版本Link Startup固定从PWM开始；
- UFS 5.0可以继续用G5 NRZ单眼图；
- 接收端系统探点可以冒充正式Tx Conformance；
- VNA可以穿过上电工作的SoC和UFS Device；
- 功能压力无错等于正式BER Pass；
- 所有UFS器件共用一套电压、时序和REF_CLK要求；
- 公开仪器页面上的旧Limit就是当前规范。

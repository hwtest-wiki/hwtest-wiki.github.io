# 同一个USB-C口，充电和显示都正常，为什么Thunderbolt/USB4硬盘还会掉速断连？

<div class="article-meta"><span class="badge">📘 模块六 · 高速接口一致性测试 · 第 9 篇 · 通用高速扩展 · Thunderbolt / USB4</span><span class="badge">⏱ 约 70 分钟</span><span class="badge qr">🔧 含工程师速查</span></div>


同一台笔记本、同一个USB-C口、同一台USB4/Thunderbolt Dock。单独接4K显示器，画面稳定；单独跑Dock里的NVMe SSD，也能识别并持续读写。可一旦显示和存储同时满载，SSD吞吐会突然往下掉，偶尔整台Dock还会断开，再重新枚举一遍。

换成普通USB3线，SSD仍然能用，只是系统不再进入USB4。把显示器拔掉，SSD又恢复正常。到这里，既不能宣布“40G带宽不够”，也不能直接判线材不合格。

因为现在还缺三组关键证据：

1. 当前到底进入了USB4、Thunderbolt兼容模式，还是只剩USB3？链路速率、宽度和Lane Bonding是什么状态？
2. 显示、PCIe存储与USB3设备经过了哪些Router、Adapter和Tunnel？并发时谁在申请带宽？
3. 首个异常发生在Type-C/PD、USB4逻辑层、Tx/Rx、Cable/PCB Channel，还是Retimer前后的某一个电气段？

这篇文章就沿着这三组证据往下拆。开场现象只负责把问题触发出来，不负责替我们宣布根因。

![图1：同一台笔记本和同一台USB4/Thunderbolt Dock中，4K显示与NVMe SSD单独运行均正常，并发后出现吞吐下降或Dock重连；图中同时保留Cable、Router/Tunnel、Retimer和供电问号，用来证明现象不能直接等同于“带宽不足”或“线材故障”](/images/43/ill01_case.png)

## 第1章　接口是什么、应用在哪里

USB-C、USB4和Thunderbolt经常出现在同一个产品页面上，三者却不是同一层概念。

### 1.1 USB-C先管“怎么接”，不承诺“跑多快”

USB-C描述的是连接器、插头方向、线缆、角色和相关连接管理体系。一个USB-C口可能只有USB 2.0，也可能支持USB 3.2、DisplayPort Alt Mode、USB4或Thunderbolt；能充电，更不代表一定具备高速数据能力。USB Type-C规范负责定义连接器与线缆相关机制，USB4能力还要由Host、Device、Cable和系统配置共同支持。〔S8〕

所以看到椭圆形接口，最多只能确认“它长得像USB-C”。要判断实际能力，还得继续看：

- Host端控制器和Router支持什么；
- Cable Identity报告了什么能力；
- Dock端能进入什么模式；
- 系统最终协商出了什么速率和宽度；
- 产品是否通过对应USB-IF或Thunderbolt认证。

### 1.2 USB4是一套Router Fabric，不是普通Alt Mode

USB4把PCIe、DisplayPort和USB3等原生协议流量封装后，通过Router转发。Host与Dock内部都有Router、Lane Adapter和Protocol Adapter，Connection Manager负责发现拓扑、配置Path并管理Tunnel。〔S1〕〔S2〕

这也是为什么同一个USB-C口可以同时挂：

- 显示器；
- PCIe/NVMe存储；
- USB键鼠、摄像头或采集卡；
- 网卡；
- 某些平台上的eGPU；
- Dock的充电与供电路径。

供电和高速数据会在同一个连接器生态里协作，但它们不是同一条协议流。充电成功只能证明电源协商和供电路径至少部分工作，不能替USB4 Router和Tunnel背书。

### 1.3 Thunderbolt是一套技术与认证生态

Thunderbolt 3、4、5都使用USB-C连接器，但Thunderbolt不等于USB-C，也不能简单等同于USB4。

- Thunderbolt 3是USB4的重要技术基础之一，公开能力最高到40Gbps；
- Thunderbolt 4仍是40Gbps等级，但增加了Intel认证范围内的强制能力与互操作要求，不能写成“USB4换了一个Logo”；
- Thunderbolt 5建立在USB4 Version 2.0等技术基础上，常规模式提供80Gbps双向能力，Bandwidth Boost是优势方向120Gbps、反向40Gbps，不是双向各120Gbps。〔S10〕〔S11〕

一台写着“USB4”的Host，可能不具备Thunderbolt认证要求的全部能力；一台Thunderbolt Dock也会根据Host、Cable和自身能力协商到共同支持的模式。最终跑在哪个模式，必须看枚举和链路证据，不能只看外壳Logo。

## 第2章　传输原理和代际差异

### 2.1 五个角色先认清

USB4拓扑里最容易混的五个词，可以顺着一笔数据的旅程理解。

**Protocol Adapter**靠近原生协议控制器。它把PCIe、DisplayPort或USB3流量封装成USB4可转发的数据，另一端再解封回原生协议。

**Router**位于USB4 Fabric的节点中，按照Connection Manager配置的路径转发USB4包。它关心拓扑、Adapter和Tunnel，不是一个“更高级的Retimer”。

**Lane Adapter**靠近物理链路，负责链路训练、速率与宽度协商、Lane Bonding以及相邻Router之间的链路工作。

**Tunnel**是承载某种原生协议流量的逻辑通道。DP Tunnel、PCIe Tunnel和USB3 Tunnel共享已经建立的USB4链路，不会永久各占一根物理Lane。

**Connection Manager**负责发现Router与Adapter、配置Path、建立或拆除Tunnel，并参与带宽管理。Windows公开资料还提供了Connection Manager事件和Trace的观察方法，适合系统Debug时还原枚举过程。〔S14〕〔S15〕〔S16〕〔S18〕

一条典型数据路径可以写成：

> PCIe / DisplayPort / USB3原生控制器 → Protocol Adapter → Host Router → Lane Adapter → USB4物理链路 → Dock Lane Adapter → Dock Router → Protocol Adapter → 下游设备

![图3：Host Router与Dock Router之间由Lane Adapter建立USB4链路，DP、PCIe和USB3 Protocol Adapter把原生流量封装成不同Tunnel；Connection Manager配置Path和带宽，图中包流动态共享链路而不绑定固定物理Lane，用来证明Tunnel是逻辑路径而不是线缆中的专属Lane](/images/43/ill03_tunnel.png)

### 2.2 DP Tunnel和DP Alt Mode必须分开

两种方式都能让USB-C口输出画面，走法却不同。

| 对比项 | DP Alt Mode | DP Tunneling |
|---|---|---|
| 进入条件 | Type-C进入DisplayPort Alternate Mode | 先建立USB4 Fabric |
| 高速通道用途 | Type-C高速对被配置为原生DP传输 | DP流量经Protocol Adapter封装成USB4包 |
| 与其他业务关系 | 取决于Pin Assignment和产品设计 | 与PCIe、USB3等Tunnel共享USB4链路 |
| 主要证据 | Alt Mode协商、DP Link状态 | Router/Adapter枚举、DP Tunnel与带宽分配 |
| 常见误判 | 有画面就说USB4已建立 | 把DP Tunnel画成固定占两根Lane |

VESA分别公开了DisplayPort 2.1与DP Alt Mode的边界；USB4里的DP Tunneling应回到USB4 Router架构理解。〔S12〕〔S13〕

因此，USB4不是普通Alt Mode。系统即使没有成功进入USB4，也可能通过DP Alt Mode继续出画面；反过来，在USB4模式中，DP业务又可以作为Tunnel与存储流量并发。

### 2.3 Tunnel共享带宽，不是把Lane切成几块

建立USB4链路后，DisplayPort、PCIe和USB3流量以包的形式共享传输资源。Connection Manager和相关Adapter根据业务需求管理路径和带宽。显示负载升高时，PCIe存储可用吞吐可能变化，但这只是一种待验证的系统行为，不等于“DP固定抢走了一根Lane”。

看并发问题时，正确的问题是：

- 当前有哪些Tunnel？
- 每个Tunnel连接了哪些Adapter？
- 当前链路速率和宽度是多少？
- 显示模式改变后，带宽分配与流控发生了什么变化？
- 首个错误是吞吐下降、重训练、Router移除，还是PD层先掉了？

![动图1：DP、PCIe与USB3数据包随业务负载在同一条USB4链路中动态交错，显示负载增加时包占比变化但物理Lane不被永久划给某个Tunnel；动画要证明带宽共享和Tunnel调度，避免形成“DP固定占两根线”的错误印象](/images/43/anim01_tunnel_bw.gif)

### 2.4 第一代USB4的20与40怎么来

第一代USB4使用64b/66b编码。公开线速关系可以用来理解链路等级：

Gen2×2 = 10.3125 Gb/s/lane × 2 lane × 64 ÷ 66 = 20 Gb/s

Gen3×2 = 20.625 Gb/s/lane × 2 lane × 64 ÷ 66 = 40 Gb/s

这里的“×2”表示两条物理Lane参与链路，不是两条PCIe Lane，也不是给DP和SSD各分一条。

Gen3单个bit的单位间隔为：

UI = 1 ÷ 20.625 GHz ≈ 48.5 ps

不到50ps的UI说明，连接器、过孔、线缆、Mux、ESD器件和Retimer两侧的时序余量都很紧。这个计算只解释时间尺度，不代替当前Electrical CTS中的正式判据。

### 2.5 20、40、80与120/40的边界

| 技术 | 公开链路能力 | 工程上应怎样写 |
|---|---:|---|
| USB4 Gen2×2 | 20Gbps/方向 | 两Lane组成20Gbps链路等级 |
| USB4 Gen3×2 | 40Gbps/方向 | 两Lane组成40Gbps链路等级 |
| USB4 Version 2.0 Gen4 | 80Gbps双向；可选120/40 | Gen4使用PAM-3；非对称模式是优势方向120、反向40 |
| Thunderbolt 3 | 最高40Gbps | USB4的重要技术基础之一 |
| Thunderbolt 4 | 40Gbps认证能力 | Intel认证与强制能力要求，不能说成USB4改名 |
| Thunderbolt 5 | 80Gbps双向；Bandwidth Boost 120/40 | 不是双向各120，也不是所有业务都能独占120 |

USB4 Version 2.0公开了80Gbps及可选120/40能力；具体产品是否支持、何时进入非对称模式，仍取决于Host、Device、Cable、固件和业务。〔S1〕〔S2〕

### 2.6 40Gbps除以8，不是SSD最低5GB/s

40Gbps ÷ 8 = 5GB/s

这只是bit与byte的理想单位换算。真实SSD吞吐还要经过：

- USB4包与流控；
- PCIe或USB3 Tunnel开销；
- PCIe、NVMe或USB Mass Storage协议开销；
- DisplayPort等并发Tunnel占用；
- Dock内部PCIe链路能力；
- SSD控制器、闪存、驱动和文件系统；
- 系统电源、温度与测试负载。

所以“40Gbps Dock的SSD必须达到5GB/s”不是合规判据，也不是合理的产品结论。更稳妥的办法，是同时记录链路状态，并做直连、Dock单盘和显示加SSD并发三组归一化比较。

## 第3章　正确使用与设计注意事项

USB4系统不是“Host口—一根线—Dock口”这么简单。真实路径可能是：

> SoC / Host Router → 主板无源段 → Retimer输入 → Retimer输出 → Mux / USB-C Receptacle → Cable → Dock入口 → Dock Retimer → Dock Router → 下游Adapter

### 3.1 正反插会换物理路径

USB-C支持正反插，Mux、Connector针脚、Retimer方向配置和Lane映射都会参与路径选择。两种插头方向在协议上应实现等价功能，电气上却可能经过不同触点、不同Mux支路或不同Lane映射。

因此“只在一个插头方向失败”是很强的隔离证据，但还不是根因。下一步要比较：

- Cable方向与插头方向；
- Current Link Width与Lane Bonding；
- Mux和Retimer方向配置；
- 对应Connector触点与PCB段；
- Host到Dock、Dock到Host两个传输方向。

### 3.2 Cable Identity、E-Marker与认证不是一回事

系统通过Type-C/PD相关流程读取Cable Identity，了解线缆声明的能力。E-Marker是线缆内用于报告身份和能力的信息器件，但“读到了E-Marker”不等于线缆已通过USB-IF或Thunderbolt认证。认证还涉及适用测试、产品标识、TID或Intel认证记录。〔S8〕〔S9〕

线缆至少要分成下面几类：

| 线缆类型 | 核心结构 | 主要验证方法 |
|---|---|---|
| 被动全功能线 | 铜线、连接器、E-Marker | Identity、标识/TID、被动S参数、Cable CTS |
| 主动Redriver线 | 模拟均衡与增益 | Identity、方向、功能、主动线适用测试 |
| 主动Retimer线 | CDR、重新判决与发送 | 两侧Tx/Rx、BERT、训练、协议与固件 |
| Thunderbolt认证线 | Intel认证范围内的能力 | Logo、代际、速率、认证产品记录与Interop |

不能给所有USB4线写一个统一“最长X米”。代际、线规、被动或主动结构、损耗预算和认证范围都可能不同。文章里只写一刀切长度，反而会把选线带偏。

### 3.3 Redriver、Retimer和Router别混用

| 器件 | 主要工作 | 是否恢复时钟并重新发送 | 是否处理USB4 Tunnel |
|---|---|---:|---:|
| Redriver | 模拟增益、均衡、边沿补偿 | 通常否 | 否 |
| Retimer | CDR、判决、重新发送 | 是 | 通常不终结Tunnel |
| Router | 转发USB4包、连接Adapter和Path | 不是其主要定义 | 是 |

Redriver会放大和整形模拟信号，也可能把噪声一起带过去；Retimer把输入判决成数据后重新产生输出，前后不再是一条连续的模拟通道；Router工作在USB4架构层，负责包和Tunnel。

### 3.4 Retimer前后是两个电气段

这是整篇最重要的物理边界之一。

假设Host主板上有一颗Retimer，那么至少要拆成：

1. SoC/Router Tx到Retimer Rx的无源段；
2. Retimer自身的输入容限、CDR、均衡、固件和温度行为；
3. Retimer Tx到USB-C Connector的无源段；
4. Cable与Dock入口；
5. Dock内部下一颗Retimer或Router前后的独立段。

VNA可以测两侧断电、隔离后的无源PCB和Connector，却不能用一条端到端S21把Retimer“穿过去”。Retimer输出应作为新的Tx观察，Retimer输入应作为新的Rx压力对象。把前后幅度差直接叫“整条Channel插损”，物理含义已经错了。

![图4：从Host SoC/Router经过主板无源段、Retimer、Connector、Cable到Dock Router的真实路径；Retimer前后用两个独立参考面和两段波形表示，图中不画连续S21穿越Retimer，用来证明有源重定时器必须拆成Rx、Tx和两侧无源Channel分别评估](/images/43/ill04_physical.png)

### 3.5 布板、供电、温度和固件要一起留证据

高速路径设计至少要检查：

- Connector、Via、层转换、ESD器件与测试Pad的阻抗连续性；
- 差分对内Skew、Lane间差异与完整回流路径；
- Retimer/Mux的摆放、参考时钟与敏感电源；
- 正反插两条路径是否对称；
- Dock入口和内部Connector是否形成额外不连续；
- Retimer与Dock控制器的散热；
- VCONN、Dock供电与并发负载下的电压稳定性；
- BIOS、驱动、Connection Manager、Retimer和Dock固件版本。

测试前必须冻结这些版本。否则换了一根线、升级了Dock固件、系统又自动更新了驱动，A/B结果就失去可比性。

## 第4章　一致性测试测什么

USB4一致性不能缩成“跑一张眼图”。电气、连接管理、协议和互操作分别回答不同问题，至少要覆盖六类对象。

| 测试对象 | 核心问题 | 主要工具 | 不能证明 |
|---|---|---|---|
| Tx | DUT发出的USB4电气信号是否满足适用要求 | 实时示波器、Compliance Fixture、自动软件 | Tunnel一定正确 |
| Rx | 最坏但合规输入下能否维持目标接收性能 | BERT、压力通道、校准示波器、Loopback/计数器 | 外部Cable一定合规 |
| 被动Channel | PCB、Connector、被动Cable是否满足无源预算 | 多端口VNA、TDR、校准件、Coupon | Retimer之后的系统性能 |
| Type-C/PD | Attach、读线、Enter_USB和角色切换是否正确 | PD Analyzer/Exerciser | 20/40/80Gbps PHY Margin |
| USB4逻辑/协议 | Router、Adapter、Path、Tunnel与适用TMU功能是否正确 | USB4CV、协议Exerciser/Analyzer | Tx/Rx电气合规 |
| Interop | 多厂商Host、Dock、Cable、显示、SSD在真实状态下是否可靠 | 设备矩阵、自动负载、日志与时间同步 | 每个PHY项目都通过 |

USB-IF公开的Compliance入口、Electrical CTS、USB4CV CTS、Product Test Matrix和Interop Procedure，本身就说明USB4认证不是单项测试。〔S3〕〔S4〕〔S5〕〔S6〕〔S7〕

![图5：六类USB4测试矩阵横向覆盖Tx、Rx、被动Channel、Type-C/PD、USB4逻辑/协议和Interop，纵向标出Host、Cable与Dock对象；图中每一格注明能回答与不能替代的证据，用来证明眼图、协议Trace或功能压力测试都不能单独代表完整一致性](/images/43/ill05_matrix.png)

### 4.1 正式Compliance与真实笔记本Debug要分开

正式Host Tx或Rx测试，要使用适用CTS规定的Fixture、Pattern、参考面、校准和判定流程。真实零售笔记本的内部SoC到Retimer节点通常不可访问，外部USB-C口配合专用Compliance Fixture才是可审计的正式入口。

系统Debug则从外部证据开始：

1. Host USB-C外部参考面、PD Trace和链路状态；
2. 工程板SoC/Router → Retimer；
3. Retimer → Connector；
4. Cable；
5. Dock入口；
6. Dock内部Retimer/Router与下游Adapter。

内部节点只有在工程板、Interposer或芯片调试模式下才适合分段。普通飞线、长支路或随手焊上的同轴会改变原链路，只能作为Debug线索，不能冒充正式Compliance结果。

## 第5章　Tx、Rx、Channel分别怎么测（含协议与互操作边界）

### 5.1 Tx：确认“发出来的东西”是否合规

Host或Dock Tx测试的基本动作是：

1. 确认产品形态、USB4代际、方向、速率和Lane宽度；
2. 让DUT进入适用的Compliance Pattern；
3. 使用规定Fixture接到示波器，在定义参考面测量；
4. 覆盖支持的Lane、两个传输方向、插头方向和适用EQ/Preset状态；
5. 按当前Electrical CTS选择Clock Recovery、参考接收器、滤波与Embedding；
6. 保存原始波形、自动报告、校准文件和最差实例。

Tx报告可能包含眼图、幅度、Jitter、均衡相关项目和其他适用电气测量，但眼图只是其中一项。它能证明“这个Tx在当前台面下怎样发”，不能证明Router、Tunnel、Cable和远端Rx一定正常。仪器厂商公开资料可以帮助理解台面和自动化流程，正式项目仍以当前USB-IF CTS为准。〔S19〕〔S21〕〔S22〕

### 5.2 Rx：校准压力输入，再看DUT能不能收

Rx测试不能拿一台“看起来波形很差”的信号源直接撞DUT。正确顺序是：

1. BERT产生适用Pattern；
2. 按CTS加入规定的损耗、Jitter、噪声、幅度和其他压力；
3. 在Rx参考面用校准示波器确认Stressed Eye；
4. 保存每个速率、Lane、Preset与Jitter频点的校准状态；
5. 撤掉校准示波器负载，把同一参考面接到DUT Rx；
6. 让DUT进入Loopback或可审计错误计数模式；
7. 清零计数，按规定持续时间执行，再读取错误；
8. 扫完支持的方向、Lane和速率。

若产品没有可审计Loopback或错误计数，只能做系统级接收容限Characterization。比如观察Dock是否重连、吞吐是否掉档，可以帮助Debug，却不能改名为正式Rx Compliance。〔S20〕

### 5.3 被动Channel：找损耗、反射和串扰落在哪一段

被动Channel测试适用于断电并与有源器件隔离后的：

- SoC/Router到Retimer输入的PCB段；
- Retimer输出到Connector的PCB/Mux段；
- 被动Cable；
- Dock入口到Dock Retimer/Router的无源段；
- Connector、Coupon和Fixture。

常用动作包括：

- 多端口VNA测差分插损、差分回损、串扰和模式转换；
- TDR定位Connector、Via、ESD或测试Pad的阻抗突变；
- 比较正反插对应路径；
- 使用2×Thru、TRL、SOLT或项目认可方法校准/去嵌；
- 保存参考面定义和Fixture S参数。

主动Redriver线和Retimer线不能套用纯被动Cable的端到端S参数结论。Redriver线要按主动线流程验证方向、增益、功能和训练；Retimer线要分别看两侧Tx/Rx、协议与固件。

### 5.4 Type-C/PD、USB4逻辑与Interop：各守各的边界

Type-C/PD测试关注Attach、插头方向、VCONN、Cable Identity、Enter_USB和角色行为。进入USB4需要完成必要的连接管理和消息流程，但不能写成“必须先完成高压快充协商才能进入USB4”。具体SOP、SOP'、SOP''顺序和字段，应回当前Type-C规范与项目PD Trace确认。〔S8〕

USB4CV与协议分析关注：

- Router和Adapter是否正确枚举；
- Path和Tunnel是否建立；
- USB3、DP、PCIe Tunneling是否符合适用要求；
- 训练、流控、时间管理和错误恢复是否按测试项工作；
- 失败落在哪个Router、Adapter或Tunnel。

Interop则把真实Host、Dock、Cable、Display、SSD和电源状态组合起来，覆盖正反插、冷插、热插、睡眠唤醒、并发业务和长时间运行。它最贴近用户体验，但“跑一夜没掉”仍不是USB-IF或Intel认证结论。

## 第6章　测试环境和仪器怎么搭

### 6.1 Host Tx台面

**目标：**回答Host在USB-C外部规定参考面发出的信号是否满足适用Electrical CTS。

**台面组成：**

- 笔记本或Host DUT；
- 控制DUT进入Compliance Mode的测试控制器；
- 对应Plug/Receptacle与方向的Compliance Fixture；
- 高带宽实时示波器；
- USB4 Tx自动测试软件；
- 适用Fixture、Embedding/De-embedding文件；
- 电源、温度记录和DUT版本清单。

**接线步骤：**

1. 先确定测Host发往Dock，还是测Dock发往Host；
2. 按产品形态选Fixture和插头方向；
3. 完成示波器通道校准、Deskew和信号路径补偿；
4. 让DUT输出目标代际与速率的Compliance Pattern；
5. 按Lane、方向、速率、Preset逐项采集；
6. 保存自动报告和原始波形。

零售笔记本外部口可以通过正式Fixture形成可审计参考面；SoC旁边的普通探头点，即使波形更“好看”，也不能替代外部正式结果。

### 6.2 Receiver台面

**目标：**回答Host或Dock Rx在最坏但合规输入下能否维持规定接收性能。

**台面组成：**

- BERT或专用USB4 Receiver Test平台；
- 压力通道、Fixture与适用Embedding网络；
- 校准实时示波器；
- Host或Dock Rx DUT；
- Loopback、错误计数器或授权判错接口；
- 自动控制和结果记录软件。

**台面分两个阶段：**

**校准阶段：**BERT → 压力通道/Fixture → 校准示波器。每个速率、Lane、Preset、Jitter频点和方向都在Rx参考面完成校准并保存。

**正式接收阶段：**保持信号源与压力设置不变，撤掉校准示波器，接入DUT Rx。清零计数后执行规定Pattern和持续时间，再读取错误结果。

不能为了“边看边测”把示波器一直T接在DUT前面。额外负载会改变已校准的Stressed Eye，报告也失去有效性。

![图9：Receiver台面左侧先由BERT、压力通道和校准示波器在Rx参考面校准Stressed Eye，右侧正式测试时撤掉示波器并接入DUT Loopback/错误计数器；图注要证明校准与接收是两个阶段，不能带着额外测量负载直接判Rx](/images/43/fig_setup_rx.png)

### 6.3 Channel与Retimer分段台面

**目标：**把无源损耗与有源Retimer行为拆开，找出Margin在哪个参考面发生变化。

**无源段台面：**

- 多端口VNA或TDR；
- PCB Coupon、Connector Fixture、Cable Fixture；
- 2×Thru、TRL、SOLT或项目认可的校准件；
- 被动Cable与良品对照件。

链路断电并隔离有源器件后，分别测：

1. SoC/Router到Retimer输入；
2. Retimer输出到Host Connector；
3. 被动Cable两个方向；
4. Dock Connector到Dock Retimer/Router；
5. Dock内部其他无源段。

**Retimer有源台面：**

- Retimer输入侧作为Rx DUT，用BERT校准压力后测试；
- Retimer输出侧作为新Tx，用示波器和适用Fixture测试；
- 协议分析仪同步记录训练、速率、Lane Bonding和错误；
- 温度、参考时钟、敏感电源与固件版本同时记录。

### 6.4 系统Debug台面

**目标：**在真实并发条件下，把用户现象、连接管理、Tunnel事件、吞吐、供电、温度和物理层证据放到同一时间轴。

**建议DUT与负载：**

- 笔记本工程样机；
- 至少两根已知良好、能力明确的认证Cable；
- 目标USB4/Thunderbolt Dock和一台对照Dock；
- 固定分辨率、刷新率、色深与压缩状态的显示器；
- NVMe SSD及可重复的读写负载；
- USB3设备、网卡负载；
- Dock原装电源。

**观察工具：**

- Type-C/PD Analyzer；
- USB4协议Trace或系统Connection Manager日志；
- 链路速率、宽度、Lane Bonding与Tunnel状态读取工具；
- SSD吞吐、显示丢帧、设备枚举与错误日志；
- Dock输入电压、电流、关键电源和温度记录；
- 同步录像或统一时间戳。

系统台面先不拆机。先从Host USB-C外部证据判断故障层次，只有外部证据指向训练、方向或Margin问题，才进入工程板内部和Retimer两侧分段。

## 第7章　仪器关键设置

台面搭出来只是第一步。设置不完整，Pass/Fail再漂亮也无法复现。

### 7.1 所有测试先建立一张Setup封面

每次测试先记录：

- DUT、Host/Dock/Cable型号与硬件版本；
- USB4或Thunderbolt代际；
- BIOS、驱动、Connection Manager、Retimer和Dock固件；
- Plug/Receptacle、插头方向与数据方向；
- 目标速率、Lane宽度、Lane Bonding；
- Compliance Pattern、EQ/Preset；
- Fixture、Cable、Embedding与去嵌文件版本；
- 温度、电源状态和测试时间；
- CTS、自动软件与仪器固件版本。

### 7.2 Tx示波器设置

按下面的顺序执行：

1. 载入与DUT代际、产品形态匹配的USB4 Electrical测试应用；
2. 选择实际支持的速率、Lane、方向、Plug/Receptacle与Preset；
3. 完成探头或同轴通道校准、通道间Deskew和幅频响应补偿；
4. 按CTS要求导入Fixture去嵌或Channel Embedding文件；
5. 设置规定的Clock Recovery、参考接收器和滤波；
6. 模拟带宽、采样率与记录长度按当前CTS和自动软件要求设置，不凭经验套固定值；
7. 对每个Pattern采集足够记录，开启统计和最坏实例保存；
8. 自动测量后保留原始波形，复查软件识别的Pattern、Lane和速率是否正确。

这里最容易发生的错误，是软件选了Gen3，DUT却掉到Gen2；或者报告写Lane 0，Fixture实际接的是另一条路径。自动软件不会替你发现接线标签错了。

### 7.3 Rx BERT设置

1. 选择目标代际、速率、Lane、方向和适用Pattern；
2. 载入当前CTS要求的压力通道与Embedding；
3. 在Rx参考面逐项校准幅度、损耗、Jitter、噪声及其他适用压力；
4. 对CTS规定的每个Jitter频点保存校准结果和校准时间；
5. 确认Pattern Generator与DUT Loopback模式匹配；
6. 正式测试前清零错误计数，并记录CDR Lock、Lane Lock和Link状态；
7. 每个点按当前CTS规定的持续时间和错误判据运行；
8. 失败点要重复校准确认，避免信号源漂移或Fixture松动被误判成DUT Fail。

不要自己发明BER门槛，也不要从旧报告复制Stressed Eye数值。Rx判据必须绑定适用CTS版本和产品形态。

### 7.4 VNA与TDR设置

1. 差分链路优先使用四端口测量并转换Mixed-Mode S参数；
2. 频率范围覆盖目标代际所需分析带宽，具体范围按规范、Fixture和项目计划确认；
3. 完成SOLT、TRL、2×Thru或实验室批准的校准/去嵌；
4. 用已知Thru或Verification Coupon确认校准没有失效；
5. 记录端口扩展、参考阻抗、IF Bandwidth、激励功率和平均次数；
6. 同时保存差分插损、差分回损、近端/远端串扰与模式转换；
7. TDR记录上升时间、差分/单端激励、终端和距离换算条件；
8. 正反插路径、Cable两个方向和良品/问题件使用同一设置对比。

Time Gating可以帮助隔离Fixture，却可能同时改写真实响应。用过就必须在报告里写清窗口和目的，不能把门控后的曲线当成原始结果。

### 7.5 PD与协议分析设置

1. Analyzer在插线前开始Arm，保证捕获CC Attach之前的事件；
2. 记录插头方向、VBUS、VCONN和必要的PD通信；
3. 开启Cable Identity与Enter_USB相关消息解析；
4. 主动线场景按当前规范与工具能力记录SOP、SOP'、SOP''；
5. 保留原始Trace，不只导出过滤后的截图；
6. PD Analyzer、USB4 Trace、系统日志、吞吐工具和温度记录统一时钟；
7. 设置环形缓存或足够记录长度，确保能保留首次异常之前的数据；
8. 标记首个CC Detach、Reset、Link Retrain、Router Removal、Tunnel变化和业务错误。

### 7.6 并发业务设置

系统测试必须把“满载”写成可重复条件：

- 显示分辨率、刷新率、色深、HDR/DSC状态；
- SSD型号、容量状态、读写块大小、队列深度与测试文件；
- SSD直连基线、Dock单盘基线和显示加SSD并发结果；
- USB3与网络是否同时加载；
- 每轮持续时间、冷机/热机条件；
- 正反插、冷插、热插、睡眠和唤醒次数；
- Cable与Dock组合；
- Host和Dock温度、输入功率及节流状态。

推荐同时保存两个归一化量：

单盘归一化 = Dock单盘吞吐 ÷ SSD直连基线

并发归一化 = 显示＋SSD并发吞吐 ÷ Dock单盘吞吐

它们方便比较，不是固定合规门槛。报告仍要同时给出实际链路速率、宽度、Tunnel和环境条件。

## 第8章　判据和标准从哪里来

USB4和Thunderbolt资料很多，权威范围并不相同。

| 来源 | 能作为哪类依据 | 不能越过的边界 |
|---|---|---|
| USB-IF | USB4 Specification、Type-C Specification、Electrical CTS、USB4CV CTS、Product Test Matrix、Interop Procedure | 正式项目必须使用适用版本与授权流程，不能拿公开摘要补写受控限值 |
| Intel | Thunderbolt技术能力、公开代际说明与认证生态 | 公开Overview不替代Thunderbolt认证规范、授权工具和认证实验室流程 |
| VESA | DisplayPort与DP Alt Mode公开边界 | 不负责定义USB4 Electrical或PCIe Tunnel判据 |
| Microsoft | Windows USB4 Connection Manager实现要求、事件、Trace与设备门户 | 是Windows平台Debug依据，不是USB-IF电气限值来源 |
| 仪器厂商 | 台面、自动化软件、校准方法、协议/电气测量能力 | 默认Limit和旧版应用笔记不能冒充当前规范 |

正式判据至少按下面的顺序确认：

1. 产品宣称和支持的USB4/Thunderbolt代际；
2. Host、Device、Hub、Cable或Retimer等产品形态；
3. 适用USB4 Specification与Type-C Specification；
4. 对应Electrical CTS、USB4CV CTS、Product Test Matrix与Interop Procedure；
5. Thunderbolt产品再叠加Intel认证范围；
6. DP相关行为回VESA资料与实现要求；
7. Windows系统问题再用Microsoft Connection Manager Trace定位；
8. 最后才是仪器自动软件中的具体项目和Limit。

USB-IF公开Compliance页面与文档入口可以确认测试类别和版本；具体Mask、BER、压力眼校准值、Jitter、损耗、参考面、Embedding文件和测试向量，应从项目有权使用的现行文件与授权软件读取。〔S3〕〔S4〕〔S5〕〔S6〕〔S7〕

正文可以讲测量对象、设置流程和证据边界，但不复刻或拼凑受控限值。仪器厂商软件里即使预装了一个Limit，也要先核对它对应的规范版本、产品类型和软件发布说明。

## 第9章　报告怎么看

拿到USB4报告，先别搜索“FAIL”。先确认报告有没有资格被相信。

### 9.1 先验证报告有效

至少核对：

1. DUT序列号、硬件版本和产品类型；
2. USB4/TB代际、速率、Lane宽度与Lane Bonding；
3. Plug/Receptacle、插头方向和数据方向；
4. Compliance Pattern、EQ/Preset和测试模式；
5. 测点、参考面、Fixture、Embedding和去嵌；
6. CTS、自动软件、仪器固件与DUT固件版本；
7. 温度、电源与并发负载；
8. Tx是否覆盖全部支持Lane、方向和速率；
9. Rx Stressed Eye校准是否与正式测试一一对应；
10. Channel是否只包含声明的无源段；
11. USB4CV与协议Trace是否对应同一DUT配置；
12. Interop是否保留Cable、Dock、方向、睡眠状态和复现概率。

任何一项说不清，Pass和Fail都要先挂起。

### 9.2 再找最差组合

有效报告里，平均值通常不如最差组合有用。按报告类型找：

| 报告 | 优先找什么 |
|---|---|
| Tx Electrical | 最差Lane、方向、速率、Preset、测试项和最小Margin |
| Rx | 最差Lane、方向、速率、Preset、Jitter频点和重复性 |
| Channel | 最差频段、最差Cable方向、插损/回损/串扰/模式转换异常 |
| Type-C/PD | Cable Identity差异、Enter_USB失败、Reset或Detach首发时间 |
| USB4CV/协议 | 失败Router、Adapter、Path、Tunnel和首个协议错误 |
| Interop | 只在哪个Host/Cable/Dock/方向/电源状态组合复现 |

最值得关注的不是“有一个红格”，而是这些最差项能否互相对上。例如：

- Rx只在某个Jitter频点失败；
- Channel同一方向在对应频段出现明显异常；
- 系统又只在那个插头方向降成单Lane；
- 协议Trace中的Retrain时间与吞吐下降一致。

这条证据链比单张眼图有力得多。

![图6：一份有效报告先核对DUT、代际、速率、方向、Fixture、校准、CTS与环境，再横向关联Tx最差Lane/Preset、Rx最差Jitter频点、Channel最差频段、失败Tunnel和Interop组合；该图要证明判读顺序是“先验有效性—再找最差组合—最后限定结论”](/images/43/ill06_report.png)

### 9.3 把不同报告放到同一时间轴

并发掉速或断连时，至少对齐：

- CC Attach/Detach、PD Reset与VBUS事件；
- Cable Identity与Enter_USB；
- Link Training、Current Speed、Width和Lane Bonding变化；
- Router加入/移除；
- DP、PCIe、USB3 Tunnel建立或拆除；
- SSD吞吐下降和I/O错误；
- 显示黑屏、闪屏或重训练；
- Dock输入功率、关键电源与温度；
- Retimer错误、锁定状态和固件日志。

如果第一个事件是CC Detach，就先查连接、供电和PD层；如果PD始终稳定，先出现的是Link Retrain，再把注意力转向训练、方向与PHY Margin；如果链路状态不变，只有PCIe Tunnel吞吐下降，就继续查带宽分配、Dock下游PCIe和SSD本身。

Microsoft提供的TraceLogging、Windows Device Portal与Connection Manager Trace文档，适合在Windows平台把Router和Tunnel事件拉出来。〔S16〕〔S17〕〔S18〕

### 9.4 结论只写到证据覆盖的位置

推荐写法：

- “在USB4 Gen3×2、插头方向B、Host到Dock方向和当前Fixture参考面下，Lane 1的Tx Margin最小。”
- “问题Cable在方向B未稳定建立双Lane，替换认证Cable后Speed、Width和并发吞吐恢复；回换原Cable可复现，证据支持Cable相关问题。”
- “USB4CV的PCIe Tunnel项目失败，但Tx Electrical通过；当前证据指向逻辑/协议层，不支持把原因写成Tx眼图异常。”
- “系统压力测试未再断连，但未完成USB-IF/Intel正式认证，结论仅限当前Interop矩阵。”

不推荐写法：

- “USB4测试通过，整机没问题。”
- “眼图通过，所以Tunnel没问题。”
- “协议无错误，所以PHY完全合规。”
- “40Gbps链路，SSD必须5GB/s。”

## 第10章　常见问题如何Debug

回到开场场景：显示与SSD单独正常，并发后掉速或断连。不要一上来拆机量Retimer。完整闭环按下面的顺序走。

### 10.1 冻结复现条件

先固定：

- Host、USB-C口与插头方向；
- Cable型号、方向、认证信息和序列标识；
- Dock、Dock电源与下游端口；
- 显示分辨率、刷新率、色深、HDR/DSC；
- SSD型号、测试负载与持续时间；
- BIOS、驱动、Connection Manager、Retimer和Dock固件；
- 冷机/热机、环境温度与供电状态；
- 单负载与并发负载的复现步骤。

每轮记录首次异常时间、复现概率、Link Speed/Width、吞吐、温度和日志文件名。没有这一步，后面“换线好了”可能只是机器冷下来了。

### 10.2 先查Cable Identity与Enter_USB

从外部证据开始：

1. CC是否稳定Attach，插头方向是否识别正确；
2. VCONN和必要的PD通信是否正常；
3. Cable Identity报告了什么速率、类型和主动能力；
4. Enter_USB是否成功；
5. 系统最终进入USB4、Thunderbolt兼容模式、USB3、DP Alt Mode还是USB2；
6. 失败前有没有PD Reset、Detach或Cable消息异常。

如果系统从未进入USB4，就先解决Cable能力、连接管理、固件或策略问题。此时去量40Gbps眼图，方向已经错了。

### 10.3 再查速率、宽度与Lane Bonding

确认：

- Current Link Speed是20、40、80还是其他实际状态；
- Link Width是否为预期Lane数；
- Lane Bonding是否完成；
- 正反插是否得到同样结果；
- Host到Dock与Dock到Host两个方向是否都稳定；
- 失败时是主动降档、重训练，还是整条链路消失。

**只能USB3：**先看Cable Identity、Enter_USB、Router枚举和平台策略，再用已知良好Cable/Dock做A/B。

**20/40/80档位或宽度降级：**记录哪条Lane、哪个方向和哪次训练失败，再转向Cable、Connector、Mux、Retimer方向配置与相应Rx/Tx。

**单方向失败：**区分“插头方向A/B”与“数据传输方向Host→Dock/Dock→Host”。前者常帮助定位Mux、Connector和Lane映射，后者更接近某端Tx或对端Rx。

### 10.4 查Router、Adapter和Tunnel

链路建立后继续看：

- Host Router与Dock Router是否稳定存在；
- DP、PCIe、USB3 Adapter是否完整枚举；
- 对应Tunnel是否建立；
- 显示模式改变时带宽分配是否变化；
- PCIe Tunnel是否存在，Dock内部PCIe Link是否降级；
- Router Removal、Tunnel Tear-down或协议错误谁先发生。

**显示正常但SSD慢：**不要因为画面正常就判整条USB4健康。DP Tunnel可能正常，PCIe Tunnel、Dock下游PCIe链路、带宽分配或SSD负载仍可能异常。

**显示加存储并发异常：**比较单负载和并发时的Tunnel、Link状态、Dock功耗与温度。只有带宽变化、没有Retrain，和先Retrain再掉速，是两条不同的调查路径。

### 10.5 做换线、换Dock、正反插与单/并发A/B

推荐最小矩阵：

| A/B动作 | 主要隔离对象 |
|---|---|
| 原Cable ↔ 已知良好认证Cable | Cable Identity、损耗、主动线固件与方向 |
| 原Dock ↔ 对照Dock | Dock入口、内部Retimer/Router、供电与固件 |
| 插头方向A ↔ B | Connector触点、Mux、Lane映射与方向配置 |
| 显示单负载 ↔ SSD单负载 ↔ 并发 | Tunnel、带宽、供电、温度与业务相关性 |
| 冷机 ↔ 热机 | Retimer、Dock电源与热Margin |
| 冷插 ↔ 热插 ↔ 睡眠唤醒 | Connection Manager、重枚举和电源状态恢复 |

每次只改一个变量，并且回换原组合复现。只做“换了就好”不做回换，证据还不够闭环。

### 10.6 把首个事件钉在时间轴上

把PD、Router事件、Tunnel事件、业务错误、供电、温度和录像统一时间戳。然后问：

- 是CC/PD先掉，还是USB4 Link先Retrain？
- 是Router先被移除，还是SSD先报I/O错误？
- 是Dock温度达到某状态后出现，还是与温度无关？
- 显示黑屏和SSD掉速是不是同一时刻？
- 错误只发生在睡眠唤醒，还是持续负载也会发生？

**Dock随机断连：**优先找CC Detach、PD Reset、VBUS变化、Router Removal和Retrain的先后，不要只看Windows“设备已断开”提示。

**睡眠唤醒后不认Dock：**检查Connection Manager Trace、Router重枚举、Tunnel恢复、UEFI/BIOS Handoff、Dock与Retimer固件及电源状态。若冷插稳定、只在唤醒失败，先别把它写成纯Channel损耗。

### 10.7 外部证据指向PHY后，再做Retimer分段

分段顺序建议是：

1. Host USB-C外部正式参考面；
2. 工程板SoC/Router → Retimer；
3. Retimer输入状态与Rx容限；
4. Retimer输出Tx；
5. Retimer → Host Connector无源段；
6. Cable；
7. Dock入口；
8. Dock内部Retimer前后；
9. Dock Router与下游Adapter。

![动图2：真实系统Debug先在Host USB-C外部读取Cable Identity、Enter_USB、速率、宽度、Router和Tunnel，再通过换线、换Dock、正反插与时间轴缩小范围，最后才进入Host与Dock Retimer两侧分段；动画要证明排查顺序从低侵入外部证据逐步深入，而不是先用飞线假定内部某段有问题](/images/43/anim02_debug_path.gif)

Retimer前后要分别问：

- 输入侧Stressed Eye或真实输入是否已经接近边缘；
- Retimer是否稳定Lock，训练和错误计数是否随温度变化；
- 输出侧Tx在当前速率、方向和Preset下是否合规；
- 两侧无源段各自的插损、回损、串扰和模式转换怎样；
- 固件或Preset变化是否改善一个方向、却伤到另一个方向。

普通飞线看到的波形只能帮助判断趋势。要写正式结果，必须回到规定Fixture、参考面和校准流程。

### 10.8 按现象收口

| 现象 | 第一层证据 | 第二层证据 | 需要避免的误判 |
|---|---|---|---|
| 只能USB3 | Identity、Enter_USB、Router枚举 | 已知良好Cable/Dock、固件与策略 | 直接判40G PHY差 |
| 速率或宽度降档 | Speed、Width、Lane Bonding、方向 | 训练Trace、对应Lane Tx/Rx、Cable/Connector | 把降档写成SSD性能问题 |
| Dock随机断连 | CC/PD、VBUS、Router Removal时间轴 | 供电、温度、固件、Retimer分段 | 只看操作系统弹窗 |
| 显示正常但SSD慢 | PCIe Tunnel、下游PCIe与SSD状态 | DP带宽、Dock固件、负载与温度 | 画面正常等于USB4全正常 |
| 显示＋SSD并发异常 | Tunnel、Link状态、功耗与温度 | 流控、Retimer Margin、Dock电源 | 直接宣布40G不够 |
| 仅一个插头方向失败 | 方向、Lane Bonding、Mux映射 | Connector与对应PCB段 | 只换线不记录方向 |
| 单一传输方向失败 | 该端Tx、对端Rx与方向性Channel | Retimer方向设置、Preset和训练 | 把Host→Dock与插头方向混为一谈 |
| 睡眠唤醒失败 | CM Trace、Router重枚举、Tunnel恢复 | BIOS/固件、电源状态、Retimer唤醒 | 冷插正常就判无问题 |

### 10.9 修复后恢复原并发条件复测

修复可能来自：

- 修正Cable选择、Identity或连接管理；
- 修复Lane映射、Mux、Preset或训练配置；
- 更新Router、Retimer、Dock或系统固件；
- 改善Connector、Via、ESD、回流与无源Channel；
- 改善Retimer参考时钟、电源、散热或摆放；
- 修复Dock供电、下游PCIe链路或并发带宽策略。

关闭问题前，必须恢复最初失败条件：

- 同一Host、同一USB-C口；
- 原显示模式；
- 原SSD负载；
- 原Dock与原Cable组合；
- 原插头方向；
- 相同温度、供电和持续时间；
- 显示与SSD同时满载；
- 睡眠唤醒、热插拔等原触发步骤。

然后比较修复前后的Cable/Enter_USB、Speed/Width、Lane Bonding、Router/Tunnel、吞吐、首错时间、Retimer状态和复现概率。最终结论应能连成一句完整的话：

> 改变了什么 → 哪个可测证据改善 → 首个错误怎样变化 → 原并发故障是否消失 → 其他方向和模式有没有退化。

这才是一条完整的USB4 Debug闭环。

USB4最容易让人误判的地方，是很多层都能“部分正常”：USB-C能充电，DP Alt Mode能出画面，USB3还能识别，甚至USB4也能偶尔跑到40Gbps。可这些现象都不能替Tx、Rx、Channel、Router、Tunnel和Interop互相证明。先把当前模式、速率、宽度和拓扑说清，再把外部证据、时间轴与Retimer分段接起来，掉速和断连才不会停在“换线试试”的经验判断上。

## 第11章　🔧 工程师速查（附录）

> **第11章　工程师速查。**本附录全部为公开通用知识，不包含项目机密或受控规范限值。

### 11.1 USB-C、USB4、Thunderbolt对照

| 名称 | 所在层 | 能说明什么 | 不能自动说明什么 |
|---|---|---|---|
| USB-C | 连接器、线缆与连接管理生态 | 物理形态、方向、角色与能力发现机制 | 固定速率、USB4或Thunderbolt认证 |
| USB4 | Router Fabric与Tunnel架构 | 可承载DP、PCIe、USB3等Tunnel | 所有产品都支持40/80Gbps |
| Thunderbolt | Intel技术与认证生态 | 对应代际能力和认证范围 | 等于USB-C或“USB4换Logo” |

### 11.2 代际与计算

| 项目 | 公开关系 | 边界 |
|---|---|---|
| Gen2×2 | 10.3125 Gb/s × 2 × 64 ÷ 66 = 20 Gb/s | 链路等级，不是应用净吞吐 |
| Gen3×2 | 20.625 Gb/s × 2 × 64 ÷ 66 = 40 Gb/s | 两条USB4物理Lane，不是两条PCIe Lane |
| Gen3 UI | 1 ÷ 20.625 GHz ≈ 48.5 ps | 用于理解时间尺度，不是正式判据 |
| USB4 v2 Gen4 | 80Gbps双向；可选120/40 | PAM-3；非对称模式不是双向各120 |
| 40Gbps换算 | 40Gbps ÷ 8 = 5GB/s | 只做单位换算，不能当SSD最低性能 |

### 11.3 Router与Tunnel速记

| 对象 | 一句话职责 |
|---|---|
| Protocol Adapter | 在原生PCIe、DP、USB3与USB4 Tunnel之间封装/解封 |
| Router | 按配置Path转发USB4包 |
| Lane Adapter | 训练物理链路，协商速率、宽度并执行Lane Bonding |
| Tunnel | 某种原生协议在USB4 Fabric中的逻辑承载 |
| Connection Manager | 发现拓扑、配置Path、建立Tunnel并管理连接 |

**DP Alt Mode：**把Type-C高速通道配置为原生DP。

**DP Tunneling：**先建立USB4，再把DP流量封装为USB4包。

**禁止写法：**“DP Tunnel固定占两根Lane。”

### 11.4 Cable与E-Marker速查

- [ ] 已读取Cable Identity；
- [ ] 已确认被动线、Redriver线或Retimer线；
- [ ] 已记录Cable方向和插头方向；
- [ ] E-Marker只作为能力声明证据，没有冒充认证；
- [ ] 已核对USB-IF TID或Thunderbolt认证记录；
- [ ] 没有使用统一“最长X米”判断所有线缆；
- [ ] 主动线已按方向、Tx/Rx、训练、协议和固件测试；
- [ ] 被动Cable才使用纯无源S参数结论。

### 11.5 Redriver、Retimer、Router对照

| 器件 | 模拟均衡 | CDR/重新发送 | USB4 Tunnel |
|---|---:|---:|---:|
| Redriver | 是 | 通常否 | 否 |
| Retimer | 是 | 是 | 通常不终结 |
| Router | 不是主要定义 | 不是主要定义 | 是 |

**Retimer规则：**输入是Rx测试对象，输出是新Tx；两侧无源段分别做VNA/TDR，不能用端到端无源S21概括。

### 11.6 六类测试边界

| 测试 | 回答什么 | 不能替代 |
|---|---|---|
| Tx | 发得是否满足适用电气要求 | Rx、Tunnel、Interop |
| Rx | 最坏合规输入下能否接收 | Tx和外部Cable |
| 被动Channel | 无源段损耗、反射、串扰与Skew | Retimer与协议 |
| Type-C/PD | Attach、读线、Enter_USB与角色 | 高速PHY Margin |
| USB4逻辑/协议 | Router、Adapter、Path、Tunnel | Electrical Compliance |
| Interop | 真实多厂商组合是否稳定 | 单项正式认证 |

### 11.10 掉档与断连决策树

1. **现象能稳定复现吗？**  
   不能 → 先冻结负载、方向、温度、固件和时间；能 → 进入下一步。
2. **Cable Identity和Enter_USB成功吗？**  
   否 → 查Cable、VCONN、PD、固件和策略；是 → 继续。
3. **Current Speed、Width和Lane Bonding符合预期吗？**  
   否 → 做正反插、换线、换Dock，锁定Lane、方向和训练；是 → 继续。
4. **Router、Adapter和Tunnel完整吗？**  
   否 → 查USB4CV/协议、Connection Manager和固件；是 → 继续。
5. **单负载正常、并发才异常吗？**  
   是 → 对齐Tunnel、带宽、功耗、温度、流控和吞吐；否 → 查更基础的链路或下游设备。
6. **首个事件是CC/PD、Link Retrain、Router Removal还是业务错误？**  
   按首个事件选择层次，不从最后一条操作系统报错倒推。
7. **A/B是否跟Cable、Dock、插头方向或温度走？**  
   是 → 进入对应对象；否 → 扩展协议、供电和内部路径证据。
8. **外部证据指向PHY Margin吗？**  
   是 → 按SoC/Router→Retimer、Retimer→Connector、Cable、Dock入口和Dock内部顺序分段；否 → 留在PD/协议/系统层。
9. **修复后是否恢复原并发和睡眠唤醒条件？**  
   否 → 不能关闭；是 → 比较修复前后证据并检查其他方向是否退化。

### 11.11 正文不可写死

- USB-C等于USB4或Thunderbolt；
- Thunderbolt 4只是USB4改名；
- Thunderbolt 5双向各120Gbps；
- 40Gbps等于SSD必须达到5GB/s；
- DP Tunnel固定占用某几根物理Lane；
- USB4就是DP Alt Mode；
- 读到E-Marker就等于线缆已认证；
- 所有USB4 Cable统一最长X米；
- Redriver、Retimer和Router可以互换称呼；
- 含Retimer路径可用一条端到端无源S21概括；
- 眼图通过就证明Tunnel正确；
- 协议无错误就证明PHY合规；
- 飞线波形可以作为正式Compliance；
- 公开仪器页面上的旧Limit可以当现行规范；
- 固定Mask、BER、Jitter、损耗、压力眼和参考面限值；
- 功能压力稳定等于通过USB-IF或Intel认证。
